## Project Reflection

### DriverPass Project Summary
The DriverPass project was a systems analysis and design initiative for a client named Liam, owner of "DriverPass," a startup company created to help individuals prepare for and pass their local Department of Motor Vehicles (DMV) driving tests. Liam wanted us to design a centralized, cloud-hosted web platform that enables students to register accounts, select from three distinct training packages, complete online educational coursework and practice exams, and schedule two-hour behind-the-wheel driving sessions mapped across a 10-car vehicle fleet and assigned instructors. Additionally, the system incorporated administrative and audit tools for management and IT staff (Ian) to track reservations, manage permissions, and receive automated updates from the DMV.

### What I Did Particularly Well
I excelled at translating qualitative, conversational client interview transcripts into structured, formal technical specifications. Specifically, I effectively captured complex operational constraints such as coordinating a 10-car fleet, enforcing matching pickup and drop-off locations, and structuring role-based access controls for different stakeholders. My use case, activity, sequence, and class diagrams ensured that both technical developers and non-technical stakeholders could clearly understand system workflows.

### Areas for Revision & Improvement
If I could choose one part of my work to revise, I would expand the system design document to include a more detailed relational database schema diagram (ERD) alongside the class diagram. While the class diagram outlines core attributes and relationships, providing a fully normalized entity-relationship model with explicit foreign key constraints and database table indexes would make the handoff to database engineers even smoother during the implementation phase.

### Interpreting User Needs & The Importance of User-Centered Design
I interpreted user needs by meticulously analyzing the interview transcript between the client representatives (Liam and Ian) and our consulting team, mapping every expressed pain point and business goal into functional and non-functional requirements. It is critical to consider user needs during system design because software ultimately exists to solve real operational problems. Failing to align the system design with user workflows leads to inefficient software, user frustration, and failure to meet business objectives.

### Approach to Software Design & Future Strategies
My approach to software design is methodical and iterative, moving from high-level requirement gathering and process modeling (use case and activity diagrams) down to structural modeling (class diagrams) and technical infrastructure planning. In the future, I will continue using structured Software Development Life Cycle (SDLC) methodologies, standardized CASE modeling tools, and continuous stakeholder feedback loops to validate system behavior before a single line of code is written.
